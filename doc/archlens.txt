ArchLens                                        Human-first code relationships

ArchLens is a Neovim side pane for exploring local structure and project-level
relationships around the symbol under the cursor. It uses Tree-sitter,
attached language servers, ast-grep, and ripgrep when they are available. No
LLM or hosted service is required.

COMMANDS                                                   *archlens-commands*

                                                        *:ArchLensHere*
:ArchLensHere          Open or refresh ArchLens for the symbol under the
                       cursor.

                                                        *:ArchLensRefresh*
:ArchLensRefresh       Re-run analysis for the current focus and rebuild
                       cached module relationships. Manual section state is
                       preserved.

                                                        *:ArchLensClose*
:ArchLensClose         Close the ArchLens pane.

ArchLens does not define a global mapping. Map |:ArchLensHere| explicitly if
you want one. For example: >lua

    vim.keymap.set("n", "<leader>cm", "<cmd>ArchLensHere<cr>", {
      desc = "Explore code relationships",
    })
<

PANE MAPPINGS                                              *archlens-mappings*

The following mappings are local to the ArchLens pane:

<CR>            Open a relationship or toggle a section or context group.
f               Focus a relationship and add the previous symbol to history.
<BS>, h         Return to the previous focus.
<Tab>           Move to the next actionable row.
<S-Tab>         Move to the previous actionable row.
]s, [s          Move to the next or previous section.
<Space>, za     Toggle a section or context group.
zM              Collapse every visible section.
zR              Expand every visible section and context group.
?               Inspect the current line, or show the complete pane help.
r               Refresh the current focus.
q               Close ArchLens.

The details window opened by `?` closes with `q`, `<Esc>`, or `?`. ArchLens
keeps one details window open. Opening another details or help view replaces
it. Closing the window returns focus to the ArchLens pane.

`Sources [?]` and `Analysis [?]` mark provider lifecycle details that can be
opened with `?`. `Analysis [?]` appears while providers are active or when a
provider ends with an exceptional outcome. Active provider names remain visible
when they fit. At narrower widths ordinary running and queued work is summarized
by count; failures, timeouts, unavailability, cancellation, and retries take
priority. Completed providers do not leave persistent status noise.

`Results [?]` compacts relationship filtering, provider caveats, and bounded
analysis into one line. Its details retain each exact message. The persistent
footer shows only primary controls; press `?` on an ordinary line for the
complete pane key reference.

Semantic references covered by incoming-call occurrences are folded into the
caller row and remain inspectable with `?`. Non-call references stay separate.
When semantic calls, references, implementations, or type hierarchy
relationships exist, unmatched structural candidates start collapsed as
secondary evidence. They start expanded when structural analysis is the only
available usage source.

Type-like focuses show their Tree-sitter children as members. Language
adapters may project canonical type hierarchy relationships into familiar
roles. For example, Go interfaces distinguish satisfied contracts, extending
interfaces, and concrete implementations. Unsupported semantic type
relationships remain absent.

CONFIGURATION                                         *archlens-configuration*

Call `setup()` without options to use the defaults: >lua

    require("archlens").setup()
<

The plugin loads with defaults automatically. Later `setup()` calls merge
their options into the active configuration.

                                                    *archlens-config-sections*
Section policy controls initial collapse state and result limits: >lua

    require("archlens").setup({
      max_items = 8,
      sections = {
        collapse_secondary = true,
        default_collapsed = { "siblings" },
        hidden = { "structural" },
        max_items = {
          references = 12,
        },
        order = { "incoming", "outgoing", "references" },
      },
    })
<

`max_items` is the fallback for every section and expanded context group.
`sections.max_items` overrides it by relationship ID. Use an empty
`default_collapsed` list to start regular sections open. Set
`collapse_secondary` to false to also keep unmatched structural candidates
open when semantic usage exists. Hidden relationships are omitted from
navigation and reported by count. IDs in `order` appear first; unlisted
relationship kinds retain registry order.

                                                     *archlens-config-filters*
Project scope filters hide external, vendored, and generated results by
default: >lua

    require("archlens").setup({
      include_external = false,
      filters = {
        include_vendored = false,
        include_generated = false,
        exclude = { "third_party/legacy" },
      },
    })
<

`filters.exclude` contains project-relative path prefixes.

                                                   *archlens-config-providers*
Providers can be enabled, disabled, and bounded independently: >lua

    require("archlens").setup({
      imports = {
        enabled = true,
        timeout_ms = 5000,
        inbound = {
          enabled = true,
          command = "rg",
          timeout_ms = 8000,
        },
      },
      lsp = {
        resolve_timeout_ms = 5000,
        relationship_timeout_ms = 8000,
        cold_start_retry = {
          enabled = true,
          delay_ms = 3000,
          window_ms = 10000,
        },
      },
      grouping = {
        enabled = true,
        timeout_ms = 1500,
      },
      ast_grep = {
        enabled = true,
        command = "ast-grep",
        timeout_ms = 15000,
        max_results = 80,
      },
    })
<

See `lua/archlens/config.lua` for all current bounds and defaults. The
configuration API remains experimental.

The cold-start retry runs once only when a newly attached language server
returns no semantic relationships and no error. Warm clients complete
immediately. Set `lsp.cold_start_retry.enabled` to false to disable it.

HEALTH                                                       *archlens-health*

Run the following from a source buffer: >vim

    :checkhealth archlens
<

The report shows the selected project root, Tree-sitter adapter and parser,
attached language-server capabilities, and ast-grep availability. Missing
optional providers reduce the available relationships but do not prevent the
pane from opening.

LANGUAGE ADAPTERS                                          *archlens-adapters*

Language adapters define Tree-sitter symbols, root markers, module analysis,
relationship presentation, and ast-grep behavior. Register an additional
adapter before opening ArchLens:
>lua

    require("archlens.adapters").register("zig", {
      treesitter = {
        root_markers = { "build.zig", ".git" },
        symbol_types = {
          function_declaration = "Function",
        },
      },
      ast_grep = { language = "zig" },
    })
<

Optional `presentation.section(context, relation, row)` and
`presentation.row(context, relation, row)` hooks adapt relationship labels and
concise row names to language semantics. A section hook may return `key`,
`label`, `order`, or `show_kind`; a row hook may return `name` or `kind_name`.
A presentation key creates an independently collapsible view section while
the underlying relationship ID, direction, evidence, filtering, and details
remain canonical. Presentation hooks should treat their inputs as read-only.

If an adapter callback fails or returns an invalid value, ArchLens reports the
failure in the result details. Presentation falls back to canonical labels and
rows. Module analysis retains unaffected relationships and omits results that
depend on the failed callback.

The focused relationship graph is defined in `lua/archlens/graph.lua`.
Relationship names, directions, and ordering are registered in
`lua/archlens/relations.lua`.

PROVIDER EXTENSIONS                                       *archlens-providers*

Built-in and custom project-analysis providers share one ordered registry.
A provider decides whether it applies, starts its work, calls `done` once with
a graph delta and optional terminal outcome, and returns a cancellation
function. It may use `report` to publish a running or retrying state: >lua

    local graph = require("archlens.graph")

    require("archlens.providers").register("ownership", {
      order = 35,
      label = "Ownership",
      queued = false,
      enabled = function(_, _, config)
        local options = config.providers.ownership or {}
        return options.enabled == true
      end,
      start = function(context, bufnr, config, done, report)
        local result = graph.delta()
        -- Optional: report("retrying", { retry_delay_ms = 1000 })
        -- Add canonical graph edges, then complete the provider.
        done(result)
        return function() end
      end,
    })
<

Provider options belong under `providers.<id>`. Register relationship kinds
through `require("archlens.relations").register()` before returning edges.
The optional `report` callback accepts `"running"` or `"retrying"`; retry
metadata may contain `retry_delay_ms` and a short `message`. ArchLens records
queued, completed, and start-failure states around the provider call.

`done(result)` marks the provider completed. A provider that can classify
another terminal outcome may pass `state` and an optional `message`: >lua

    done(result, {
      state = "timed_out",
      message = "Ownership analysis exceeded 1000 ms.",
    })
<
Terminal states are `completed`, `failed`, `timed_out`, `unavailable`, and
`cancelled`. Partial graph results are retained for every terminal state. Use
`unavailable` only when the provider applies but a required dependency or
capability is unavailable. Disabled or inapplicable providers should not
start.

Every applicable attached LSP contributes location-based relationships.
Provider evidence remains separate when clients return the same row. Opaque
call-hierarchy items remain with the client that resolved the focused symbol.
